# 2.5D ТЕХНИЧЕСКАЯ АРХИТЕКТУРА (2_5D_TECHNICAL_ARCHITECTURE.md)

> **Статус документа**: Техническая спецификация Фазы 11 по визуальной трансформации игры «The House Remembers» в движке Godot 4.7.2. Документ содержит двухвариантную архитектуру (Решение A и Решение B), требования к адаптерам 2D-в-3D, риски совместимости и регламент сравнительного A/B бенчмаркинга на Android-устройствах.

---

## 1. Сравнительный Анализ Двух Реально Рассматриваемых Решений

По результатам исследований и разработки экспериментального прототипа Фазы 11A команда рассматривает **два равноправных кандидатных архитектурных решения**.

### 1.1. Сравнительная Матрица Вариантов

| Критерий оценки | **Решение A: Псевдообъёмная 2D-сцена (Ортографическая Camera2D)** | **Решение B: Гибридная 3D-сцена (3D-окружение + Sprite3D + 2D-логика)** |
|---|---|---|
| **Текущий статус в Godot 4.7.2** | Базовый код Фаз 9–10 (готовая 2D-логика) | Экспериментальный прототип Фазы 11A (3D-стена, 45° камера, Sprite3D, K-01) |
| **Визуальный объем** | Высокий (через рисованные фасады ассетов) | Настоящий 3D-объем (трехмерная геометрия стен, реальная перспектива/орто) |
| **Нагрузка на GPU / VRAM (Android)** | Низкая / Минимальное потребление VRAM | Средняя (требует оптимизации мешей, сжатия текстур и лимитов теней) |
| **Совместимость с 2D-системами** | Прямая (без адаптеров) | Требует слоя архитектурных Адаптеров (`Adapter2DTo3D`) |
| **Физика и Навигация ИИ** | Родные `CharacterBody2D`, `NavigationRegion2D` | Родная 2D-физика/A* с адаптером ИЛИ 3D-физика (`CharacterBody3D`, `NavigationRegion3D`) |
| **Освещение и Тени** | `PointLight2D` + `LightOccluder2D` | Нативное 3D-освещение (`OmniLight3D`, `SpotLight3D` + Shadow maps) |
| **Сохранения (`user://save_game.json`)** | Полная обратная совместимость $1:1$ | Совместимость через трансформер координат ($X, Y \leftrightarrow X, Z$) |
| **Риски реализации** | Артефакты Y-сортировки при сложной мебели | Потери FPS на слабых GPU, рассинхронизация 2D/3D координат |

## 2. Подробное Описание Кандидатных Архитектур

---

### 2.1. РЕШЕНИЕ A: Псевдообъёмная 2D-Сцена с Ортографической `Camera2D`

* **Суть**: Вся сцена остается в 2D-пространстве Godot (`Node2D`). Визуальный объем достигается за счет рисованных фасадов стен, мебели под углом $\sim 35^\circ-40^\circ$ и автоматической сортировки глубины `y_sort_enabled = true`.
* **Достоинства**:
  1. $100\%$ прямая совместимость со всеми существующими скриптами (`Player.gd`, `Keeper.gd`, `MansionMemory.gd`).
  2. Минимальная нагрузка на видеопамять Android-устройств.
* **Технические детали**:
  * Камера: Ортографическая `Camera2D`.
  * Сортировка: `y_sort_origin` на уровне стоп персонажей ($Y = 0$).

---

### 2.2. РЕШЕНИЕ B: Гибридная Сцена с 3D-Окружением и 2D-Логическим Слой (Прототип Фазы 11A)

* **Суть**: Окружение, стены, мебель и освещение строятся в 3D-пространстве Godot (`Node3D`). Персонажи (Игрок, Марк, Хранители) отображаются через `Sprite3D` или `AnimatedSprite3D` с фиксацией угла относительно камеры ($45^\circ$).
* **Архитектурный Слой Адаптеров (`Adapter2DTo3D`)**:
  Существующий 3D-прототип Фазы 11A **не является автоматически совместимым** со всеми 2D-системами проекта. Для его полноценной работы создается обязательный слой адаптации:

```
[Логический 2D-Слой / MansionMemory / AI FSM]
                   │
                   ▼
     [Слой Адаптеров: Adapter2DTo3D]
  ├─► Physics/Nav Adapter: Преобразование Vector2(X, Y) <-> Vector3(X, 0, Z)
  ├─► RayCast Adapter: Маппинг 2D-лучей зрения в 3D RayCast3D
  ├─► Save System Adapter: Сохранение Vector2 позиций в save_game.json
  └─► Sprite3D Facing Adapter: Разворот 2D-спрайта к 3D-камере
                   │
                   ▼
[3D Визуальный Рендерер: Node3D, MeshInstance3D, Camera3D (45°)]
```

#### Риски и Методы Их Нейтрализации для Решения B:
1. **Риск: Рассинхронизация коллизий и геометрии**: 2D-коллайдеры могут не совпадать с 3D-мешами стен.
   - *Нейтрализация*: 3D-стены генерируют упрощенные выпуклые коллайдеры (`ConvexCollisionSibling3D`), а навигация строится по нативной `NavigationRegion3D`.
2. **Риск: Перегрев и падение FPS на бюджетных Android**: 3D-тени с пространственными картами (Shadow Maps) требуют высокой мощности GPU.
   - *Нейтрализация*: Использование жесткого лимита: не более 2 динамических источников света с тенями (`SpotLight3D`), применение запеченного lightmapping для статических стен.
3. **Риск: Поломка формата сохранений `user://save_game.json`**:
   - *Нейтрализация*: Сохранение позиций продолжает запекаться строго в ортогональном $2D$-формате $(X, Y)$, где $Y_{2D} \equiv Z_{3D}$. При загрузке адаптер разворачивает вектор обратно в 3D.

## 3. Регламент Сравнительного A/B Бенчмаркинга (A/B Testing Framework)

Выбор финальной архитектуры производится на основе **сравнительных натурных замеров** двух рабочих прототипов на целевой группе Android-устройств.

### 3.1. Тестовая Матрица Замеров

| Параметр проверки | Методика замеров | Целевой порог (Pass) | Преимущество |
|---|---|---|---|
| **Визуальное качество** | Оценка объёма стен, света и глубины картинки | Экспертная оценка кодегов | Сравнение A vs B |
| **Управление и Отклик** | Лаг сенсорного джойстика при поворотах | Задержка ввода $< 50\text{ ms}$ | Сравнение A vs B |
| **Навигация ИИ (K-01)** | Тест поиска пути через 5 комнат с препятствиями | $0\%$ застреваний, плавный поворот | Сравнение A vs B |
| **Сохранения & Загрузка** | Корректность восстановления позиции из `save_game.json` | $100\%$ совпадение координат | Сравнение A vs B |
| **FPS на Android (Snapdragon 680)**| Замер средней и минимальной частоты кадров | Стабильные $50 - 60\text{ FPS}$ | Сравнение A vs B |
| **Потребление VRAM** | Замер через Godot Profiler (Performance Monitors) | $< 250\text{ MB}$ VRAM | Сравнение A vs B |
| **Термопрофиль и Батарея** | 15-минутный прогон игры на телефоне | Отсутствие критического троттлинга | Сравнение A vs B |

### 3.2. Итеративный Регламент Принятия Решений
* **ПРАВИЛО**: Отказ от Решения B (3D) **НЕ ПРОИЗВОДИТСЯ** из-за единичного неудачного теста или проседания FPS!
* Если Решение B показывает проседание FPS ($< 45\text{ FPS}$), команда проводит **3 обязательные итерации оптимизации**:
  1. Оптимизация количества полигонов 3D-мешей и разрешение Shadow Map до $512 \times 512$.
  2. Перевод статического освещения стен в запеченные текстуры.
  3. Оптимизация интервала адаптеров `Adapter2DTo3D` до $10\text{ Гц}$.
* Если после 3 итераций оптимизации Решение B сохраняет неустранимый перегрев или падение FPS, финализируется **Решение A (Псевдообъёмный 2D)** как гарант стабильности.

## 4. Матрица Коллизий (Collision Matrix)

Независимо от выбранной архитектуры, матрица слоев коллизий сохраняет свою логическую структуру:

| Layer Bit | Название слоя | Описание и узлы (2D / 3D) |
|---|---|---|
| **Layer 1** | `World_Static` | Непроходимые стены, закрытые двери, крупная мебель. |
| **Layer 2** | `Player` | Физическое тело протагониста (`CharacterBody2D` / `CharacterBody3D`). |
| **Layer 3** | `Keepers` | Физические тела K-01, K-02, K-03 (`CharacterBody2D` / `CharacterBody3D`). |
| **Layer 4** | `Interactables` | Двери, шкафы, предметы, рубильники (`Area2D` / `Area3D`). |
| **Layer 5** | `Sight_Blockers` | Перекрытие лучей зрения `RayCast2D` / `RayCast3D`. |
| **Layer 6** | `Sound_Triggers` | Скрипучие половицы, плитки-тревоги (`Area2D` / `Area3D`). |
